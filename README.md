# Помощник валидации проверок

Подсказывает валидатору, какие задачи стоит проверить в аудиторской проверке, по опыту
похожих проверок: что в них проверяли, где подтверждались нарушения, какие документы
запрашивали и какими методами работали.

Проект состоит из двух частей:

| | Кто пользуется | Где лежит | В Bitbucket |
|---|---|---|---|
| **Приложение** | валидаторы | корень папки | да — приезжает с автообновлением |
| **Сборка базы** | автор | `builder\` | нет (закрыто в `.gitignore`) |

Связь между ними — один файл `base\hints.db`: сборка его пишет, приложение только читает.

```
валидация проверок\
├── start.bat            запуск приложения
├── run.py, app.py       сервер (FastAPI), только чтение базы
├── static\index.html    интерфейс
├── base\hints.db        готовая база подсказок — в репозитории, едет с обновлением
├── updater\             автообновление из Bitbucket
├── release\             bump_version.bat — выпуск новой версии
├── launchers\           универсальный run_app.bat (как в Toolbox ARM)
├── config.yaml          настройки этого ПК (адрес обновлений, SSL)
├── VERSION, CHANGELOG.md
├── data\                служебное: логи, файлы обновления (не в репозитории)
└── builder\             ЧАСТЬ АВТОРА — см. builder\README.md
```

## Для пользователей

`start.bat` — сам найдёт Python 3.10+, создаст `venv`, поставит зависимости и откроет браузер.
Аргументы: `--port 9000`, `--no-browser`, `--host 0.0.0.0` (доступ коллегам по сети).

Внизу слева — версия программы, дата базы и кнопка «Проверить обновления».

## Для автора: выпуск новой базы

1. Новые выгрузки JSON → `builder\data\checks\`.
2. `builder\build.bat` — собрать базу (у сборки свой venv: numpy, scikit-learn).
   Проверить в приложении: `start.bat`.
3. `builder\publish.bat --no-build` — поднимет версию, запишет в `CHANGELOG.md`
   «Обновлена база подсказок: N проверок» и по подтверждению сделает commit и push.

Пользователи получат новую базу кнопкой «Обновить и перезапустить».
Подробности сборки и алгоритма — `builder\README.md`.

## Версии и автообновление из Bitbucket

Схема та же, что в Toolbox ARM. Номер версии — в файле `VERSION` (одна строка вида `1.0.001`),
история — `CHANGELOG.md`, новые версии сверху (`## 1.0.002 — 2026-10-28` и пункты списком).

**Настройка** — `config.yaml`:

```yaml
update:
  repo_url: https://<bitbucket>/scm/<проект>/<репозиторий>.git   # NaN — обновления выключены
  ref: main
  check_on_start: true
  keep: [config.yaml]
```

**Как работает.** При открытии страницы (и по кнопке «Проверить обновления» внизу слева)
сервер читает из Bitbucket один файл — `VERSION` из ветки `ref` (REST API `/raw/VERSION`, git не нужен).
Номер больше установленного — появляется окно «Доступно обновление» со списком изменений из
`CHANGELOG.md`. Логин и пароль Omega спрашиваются один раз; пароль хранится только в памяти
до закрытия программы, логин запоминается в `data/login.json`.

«Обновить и перезапустить»:
1. zip ветки скачивается в `data/update/staging` и проверяется (это этот проект, версия новее);
2. изменившиеся файлы раскладываются поверх (`VERSION` — последним), прежние копируются в
   `data/update/backup/<дата>`; при ошибке всё возвращается как было;
3. программа перезапускается через `start.bat`, страница перезагружается сама. Батники заменяются
   уже после выхода. Если изменился `requirements.txt`, `start.bat` доставит библиотеки.

Не трогаются никогда: папки `data/` (логи, служебное) и `builder/` (часть автора), `venv/`, `tmp/`, `.git/` и файлы
из `keep`. Ставить обновление и перезапускать можно только на том компьютере, где запущен сервер
(при `--host 0.0.0.0` коллеги видят версию, но обновить не могут).

Журналы: `data/logs/update.log`, перезапуск — `data/update/restart.log`.

**Выпуск новой версии:** `release\bump_version.bat` — спросит, что изменилось, поднимет номер
(`1.0.001` → `1.0.002`) и допишет запись в `CHANGELOG.md`. Ключи: `--minor`, `--major`,
`-c "текст"`, `--dry-run`. Затем коммит и push в ветку `ref`. Коммиты без смены `VERSION`
обновлением не считаются.
